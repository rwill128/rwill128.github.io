I taught a tiny GPT to use Python instead of guessing at math

A 790,000-parameter model mastered four-digit addition, failed completely at five digits, and eventually learned to hand calculations to a deterministic tool.

By Richard Williams August 11, 2026 Draft for review
0.79M parameters in the direct arithmetic model
499/500 four-digit addition answers correct
0/1,500 tests correct when either operand had five digits
1,999/2,000 balanced tool calls and final answers correct

Most AI demonstrations begin with a behavior and ask whether it feels intelligent. I wanted a test with nowhere to hide. Arithmetic gives an exact grade: the answer is right or it is wrong.

I started with Andrej Karpathy's nanoGPT, the small character-level Transformer commonly demonstrated by training it on Shakespeare. The original model learns enough names, punctuation, and cadence to produce recognizable Shakespeare-shaped nonsense. I wanted to know what the same kind of model would learn from a STEM education.

The result was not a clean story about a model learning or failing to learn arithmetic. It became an investigation into local competence, catastrophic forgetting, deceptive metrics, and the difference between generating an answer and knowing when to call a tool.

The most useful result was not that the model learned math. It was that the model learned when to stop guessing and hand the problem to something deterministic.

A tiny model and an exact test

The direct arithmetic model had about 790,000 parameters, four layers, four attention heads, and a 40-character context. I generated a text file containing equations separated by newlines. nanoGPT trained exactly as it would on any other character corpus: by predicting the next character in random windows.

37+58=95
912+4=916
903+76=979

There was no calculator, arithmetic-specific architecture, reinforcement learning, or scratchpad. At evaluation time, I supplied an equation through the equals sign, generated the answer greedily, and compared the leading number with the exact expected result.

This sounds difficult to get wrong. My first interesting result was still an evaluator bug.

The first discovery was my bug

After training on operands up to 999, the first evaluation grid showed a strange asymmetry. One-digit plus two-digit problems scored 61.7%, while two-digit plus one-digit problems scored 99.0%.

Addition is commutative, so reversing the operands should not create a gap like that. I could have treated the result as evidence about positional representations or attention. Instead, I tested the experiment.

The training examples were separated by newlines, but the evaluator used a bare prompt such as 4+54=. Because training windows could begin in the middle of a line, the model had also encountered the same suffix inside 14+54= and 204+54=. Nothing in the prompt told it that the first 4 was the beginning of the problem.

I added the same newline boundary used during training. One-digit plus two-digit accuracy jumped from 61.7% to 100%. The asymmetry disappeared.

That changed how I approached every later result. When a benchmark produces a surprising pattern, the first question should not be, "What did the model learn?" It should be, "What exactly did this test measure?"

Near-perfect mastery, then a wall

With the boundary fixed, the model learned bounded addition remarkably well. I expanded training to one million equations with operands sampled from 0 through 9,999. On fresh four-digit plus four-digit tests, it answered 499 out of 500 correctly.

Then I tested the next digit length. The result was not a gradual decline:

  • Four digits plus four digits: 499/500.
  • Four digits plus five digits: 0/500.
  • Five digits plus four digits: 0/500.
  • Five digits plus five digits: 0/500.

The model had become excellent at the task as represented in its training distribution. It had not learned an addition procedure that could simply repeat for another column. More training data moved the wall. It did not remove the wall.

Transfer existed, but it had a shape

Changing digit length might be an unusually hard test, so I tried a smaller distribution shift. I kept ordinary two-operand addition in rehearsal and trained a new expression shape, a+b+c, while restricting the third operand to values from 0 through 50.

The model transferred well to unseen third operands from 51 through 99. At 100, accuracy collapsed. After training through 200, it transferred some capability to unseen three-digit values before collapsing again at 1,000.

This was real generalization, but it was not unlimited. Inside a familiar digit representation, the competence had a soft edge. At a new number of digits, it had a wall.

Competence could move without becoming reusable

I then created a deliberately strange continuation. Starting from the model trained on third operands through 200, I skipped the next 499 values and trained only on third operands from 700 through 799.

If the model had learned a reusable operation, the old region might remain intact and the two regions might connect. Instead, the new 700 to 799 band reached 98.3%, while the previously learned region below 200 collapsed to about 2.8%. Ordinary two-operand addition remained at 99.6%.

The forgetting was specific. It had not globally forgotten addition; it had overwritten behavior associated with the third-operand role.

The errors were highly structured. In a 50,000-case probe of third operands from the 800s, 89.3% of predictions were exactly 100 too small. The lower digits were often preserved while the leading 8 behaved like the recently trained leading 7.

This looked less like a stable algorithm and more like a precise local map of familiar input and output shapes. That map could be expanded, shifted, erased, and restored through rehearsal.

Knowing two operations was not the same as composing them

Next, I trained multiplication while rehearsing addition. Pure multiplication training pushed two-operand multiplication above 90%, but initially erased addition. Mixed rehearsal eventually produced a checkpoint that retained strong four-digit addition and reached 96.8% on two-digit multiplication.

Then I froze the checkpoint and tested whether it could combine those learned operations in expression shapes it had not seen:

  • a*b*c: 0/2,000.
  • a*b+c: 0/2,000.
  • a+b*c: 0/2,000.

The model still produced numeric-looking output 94.5% to 100% of the time. It recognized the format. It did not perform the requested computation. Even appending an identity operation failed: a*b*1 was correct only 11 times out of 9,801.

The network could contain successful regions for addition and multiplication at the same time. It still could not call those capabilities wherever the symbols appeared.

A green evaluation can still be wrong

I expanded the curriculum into four 12-by-12 operand-length grids for addition, subtraction, multiplication, and division. Watching the cells improve and regress was useful, but division demonstrated how easily a green chart can lie.

The first generator used integer division. When the numerator was smaller than the denominator, 3/100 became 0. Large regions turned green because predicting zero was enough.

I changed the task to two decimal places and filtered out results that rounded to 0.00. That removed one shortcut and created another. In one band, 503 of 509 surviving targets were exactly 0.01. Predicting that constant was 98.8% accurate.

The model was doing exactly what optimization rewards: exploiting the target distribution. The mistake was assuming that the score represented general division before inspecting what made each cell easy.

Give the model a different job

At this point, building a more elaborate neural calculator felt like the wrong objective. A language model does not need to reproduce arithmetic internally when a deterministic calculator already exists.

I returned to the Tiny Shakespeare checkpoint and trained one small model to perform two jobs:

  1. Continue generating prose when given Shakespeare.
  2. Emit an @ sentinel and a Python expression when given arithmetic.
Q: What is (842+159)*73?
A: @(842+159)*73
R: 73073
A: 73073

The generated expression passed through a restricted parser that allowed numeric constants and approved arithmetic operators, not unrestricted Python execution. The result then returned to the model so it could finish the response.

This separated the task into stages that could be measured independently:

  • Did the model route the request to Python?
  • Was the generated expression syntactically valid?
  • Did the expression represent the requested calculation?
  • Did the final answer correctly use the returned result?

Routing succeeded before argument construction

After 1,000 updates, the model chose Python for every arithmetic prompt. That looked like success until I examined the generated arguments. Only 3.5% of the calls represented the requested calculation.

It had learned the easiest structural distinction first:

Shakespeare -> continue prose
Arithmetic  -> emit @ and call Python

It knew when to ask for help before it knew what to ask.

A later narrow evaluator reported 99.5% semantic-call accuracy. But that evaluator reused familiar operand shapes. On a balanced 2,000-case test that varied operand widths and expression roles independently, correct calls fell to 52.2% and complete answers to 46.35%.

The first evaluator bug involved one missing boundary character. This one involved sampling. In both cases, the model looked more mysterious than it was because the evaluation failed to isolate the behavior I thought it measured.

The tool-trained model becomes useful

I broadened training so operand widths and expression roles varied independently, while keeping half of each batch as Shakespeare. After 6,000 additional updates, the same balanced evaluator reached 1,999 correct calls and final answers out of 2,000.

The model also made zero false tool calls across 1,000 sampled Shakespeare contexts. Its Shakespeare validation loss improved slightly, from 1.590 to 1.573, rather than collapsing under the mixed curriculum.

Then I ran the same four 12-by-12 operand grids used for direct arithmetic. The tool model generated 5,757 semantically correct Python expressions out of 5,760. All three misses occurred in the 12-digit by 12-digit division cell.

There was still an important failure after the correct call. Across those long-operand surfaces, the tiny model recopied only 4,511 of the 5,760 returned answers correctly. The tool had produced the right value, but asking a character model to reproduce a long result created a new lossy step.

That distinction matters in production. If the deterministic system has already produced the answer, the application should usually return or render that structured result directly. It should not require a probabilistic model to copy it perfectly unless language generation adds real value.

More complex calls, within learned grammars

Finally, I trained five expression grammars containing five operands, mixed operators, and parentheses. On 1,000 unseen numerical combinations inside those learned grammars, the model generated 1,000 correct calls and recopied 998 answers.

This did not mean the model had become a general parser. When entire expression grammars were withheld, performance stayed near 53%. The tool removed the need to generalize arithmetic across new values, but the model still depended on training coverage for the symbolic structures it had to translate.

What I would carry into a production agent

The arithmetic task was intentionally small. The failure modes are not. A customer-facing agent can select the correct API and still submit the wrong customer ID, date range, operation, or medication. A successful HTTP request is not the same thing as a successfully completed task.

Evaluate the whole execution path

  • Routing: Did the model select the right capability?
  • Arguments: Do the parameters preserve the user's request?
  • Validation: Can cheap deterministic checks reject malformed or unsafe calls?
  • Execution: Did the tool complete successfully?
  • Completion: Did the system deliver the correct result to the user?

The experiment also reinforced four practical rules:

  1. Interrogate surprising metrics. A dramatic result may come from a prompt boundary, target imbalance, or evaluation shortcut.
  2. Hold out structures, not only values. New numbers inside a learned grammar are a much easier test than genuinely new task forms.
  3. Use deterministic systems for deterministic work. Let the model recognize intent and translate it into a constrained operation. Let code perform the calculation.
  4. Do not add a probabilistic recopy step. Preserve structured tool output whenever the application can present it directly.

The direct model became almost exactly as capable as the examples it received, with a few narrow and interesting exceptions. The tool-trained model did not become a mathematician either. It learned something more useful: recognize the task, preserve its structure, and hand exact execution to a system that already knows how to do it.

Pattern recognition chose the tool. Deterministic execution supplied the arithmetic. Rigorous evaluation told me whether the combination actually worked.

Where this goes next

The next experiments should test more realistic translation problems: natural-language arithmetic, unseen paraphrase templates, malformed inputs, and execution-repair loops. Those tests will make the model's actual responsibility progressively closer to the argument-construction problem inside a production agent.
