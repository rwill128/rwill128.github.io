The result, in plain English

Imagine a future error-corrected quantum computer as a floor covered with square tiles. Each logical qubit occupies a tile, and temporary pathways between tiles let the machine perform joint operations. Some tiles can begin in either of two orientations. Turning a tile can make later pathways shorter—or longer.

CircLS is a research compiler that draws this kind of lattice-surgery plan. It runs on an ordinary computer, but its output is a modeled physical quantum circuit: surface-code patches, syndrome-extraction rounds, routing space, and a Stim circuit. It does not turn a quantum algorithm into a classical algorithm.

The tested idea is simple: try turning one logical-data tile, rebuild the complete quantum-computer layout, and keep the turn only if the new verified layout occupies less space over time without taking more rounds. Repeat until no single turn helps.

The narrow result is that orientation-aware search found lower occupied-spacetime CircLS layouts on the tested Clifford benchmarks. It did not improve the underlying quantum algorithms, run on hardware, or establish a real-device speedup.

What kind of compiler is this?

The target is a fault-tolerant quantum computer using surface-code patches and lattice surgery. The layers are:

logical Clifford QASM or Pauli-product program
        ↓
classical CircLS compilation and layout search
        ↓
modeled lattice-surgery schedule and physical Stim circuit
        ↓
classical verification/simulation of that quantum circuit

The classical host—macOS or Linux—runs the compiler. The thing being optimized is the compiler's modeled quantum-circuit output, not the compiler's running time.

The precise claim to reproduce

For each benchmark, compare CircLS's released full configuration with the endpoint of the coordinate search below. A positive result requires:

  • strictly lower V1, CircLS's occupied tile-round sum divided by code distance;
  • non-increasing T1, the number of physical measurement layers;
  • byte-identical screen and verification recompilations; and
  • every public verification field run and pass, with no skipped field.

At the original code distance d = 3, V1 is Σ occupied_tiles(round) / 3. It is a compiler-model resource metric—not elapsed hardware time. The source definition is in CircLS's metric implementation.

The complete search method

The reported rows used two explicitly different greedy search profiles. Because candidate order can change a greedy path, a clean-room reproduction must use the profile assigned below rather than silently substituting one for the other.

Profile A: exhaustive physical ranking

Use Profile A for teleport_8, bv_n14, twistedghz_8, bv_n19, dj_16, and bv_n30.

The original Profile A runs used 256 noiseless verification shots. For clean reproduction, set force_distance=True on every baseline and candidate verification even where CircLS would run the distance check without forcing it.

  1. Compile the exact QASM with the released full configuration at distance three. Do not provide a placement or orientation override. Record the realized data-patch orientations, placement, V1, T1, Stim text SHA-256, and verifier report. This is the baseline.
  2. Set the current orientation map to the complete realized orientation of every non-y* data patch. CircLS's y* ancillas remain pinned by the compiler.
  3. Construct the complete one-coordinate neighborhood: for each data patch, copy the current full map and change only X_horizontal ↔ X_vertical for that patch.
  4. For each candidate, rerun CircLS optimized assignment and the complete physical compilation. Do not reuse the current or author placement. A compile failure is a rejected candidate.
  5. A screened candidate is eligible only when its V1 is strictly lower than the current V1 and its T1 is no greater than the current T1.
  6. Sort eligible candidates by V1, then T1, then ordinary Python string order of the patch name. Thus q10 sorts before q2. Recompile them independently in that order.
  7. Require the second compilation to match the first candidate's Stim SHA-256, V1, and T1 exactly.
  8. Run CircLS verification with force_distance=True. Require silence, deterministic observables, graphlike distance equal to d = 3, and logical affine structure all to run and pass. Reject any skipped field.
  9. Accept the first eligible fully verified candidate. Its full orientation map becomes current.
  10. Repeat from step 3. Stop only after physically compiling the entire final one-flip neighborhood and finding no acceptable move.

This is deterministic coordinate descent once the compiler's placement routine is fixed. The endpoint is a verified one-flip local optimum, not a global optimum.

Profile B: route-ranked continuation

Use Profile B for bv_holdout_12, dj_holdout_12, teleport_holdout_6, twistedghz_holdout_6, random_holdout_12_60_303, and the four parallel_holdout_* cases.

The original Profile B verification gates used 1,024 noiseless shots and force_distance=True.

Compile and verify the baseline exactly as in Profile A. For the baseline's complete one-flip neighborhood, physically compile every coordinate, apply the same V1/T1 eligibility rule, rank by V1, T1, and ordinary Python patch-name order, then independently recompile and fully verify the first acceptable candidate. If none is acceptable, the baseline is the endpoint.

After that exact first move, continue as follows:

  1. Build the current mapping and every one-flip mapping using released optimized assignment.
  2. Run the pure parallel-window route probe on the current mapping and every candidate. Reconstruct liveness and step batching, probe every planned merge window, demote an unroutable parallel batch to its serial windows, and return OK only if every resulting window can be routed.
  3. Rank OK candidates by parallel-window cost—the sum, over predicted windows, of active patch slots plus unique corridor cells—then route-cell count, then ordinary Python patch-name order. Retain only candidates whose cost is below the current mapping's cost.
  4. In that order, physically compile each retained candidate. If it is V1/T1 eligible, independently recompile it, require an exact hash and metric match, and run the complete verifier. Accept the first fully verified candidate.
  5. If no proxy-ranked candidate is accepted, physically compile every coordinate not already screened. Combine them with the screened candidates, rank exact eligible results by V1, T1, and patch name, and independently recompile and verify them in order. Accept the first fully verified candidate.
  6. Repeat. Stop only when the fallback in step 5 has physically covered the complete current neighborhood and no candidate is acceptable.

In the narrower regime where current and candidate preserve liveness, absence, batch structure, merge-window count, T1 latency, and zero rotations, the observed distance-three identity was:

delta V1 = ((rounds + 1) / d) × delta route cells
         = (4 / 3) × delta route cells

Outside that narrow regime the score is only a heuristic ranker, not an exact V1 prediction. Profile B still used it for ordering whenever the probe returned OK. That is safe against a false accepted metric because every accepted move is physically compiled twice and fully verified, but it can change the greedy path. The proxy also cannot certify termination; only the exhaustive physical fallback can do that.

What “verified” means here

Use the pinned public CircLS verifier. Every accepted baseline and endpoint must have:

  • silent: no detector fires in noiseless sampling;
  • deterministic: program observables are constant where expected;
  • distance: the shortest graphlike error has length three, forced even above the normal detector cap;
  • logical: the compiled output's affine structure matches the logical source program; and
  • skipped: empty.

This is compiler and simulator verification. It is not execution on quantum hardware.

What differed between macOS and Linux

Thirteen baseline/endpoint pairs reproduced with identical hashes and metrics. Two placement histories exposed a portability defect in CircLS's spectral starting layout.

  • bv_n19: Linux chose a different baseline circuit, but V1 remained 388.667 and the endpoint remained the exact same V1 378.000, T1 104 circuit. The improvement survived; the complete experiment was not byte-identical.
  • random_holdout_12_60_303: transplanting the macOS endpoint onto Linux's newly selected placement was not an improvement. A fresh exhaustive-physical Linux search—not a transplant or a replay of the original proxy-ranked path—then found a different fully verified local optimum: V1 248.000 → 242.667, a 2.15% reduction, at unchanged T1 74.

Both hosts used NumPy 2.5.2 and SciPy 1.18.1. macOS used Apple Accelerate for BLAS/LAPACK; Linux used OpenBLAS 0.3.34. CircLS's spectral start takes the second and third Laplacian eigenvectors and fixes only their signs. That does not define a unique basis when eigenvalues repeat.

Instrumentation found a many-fold repeated eigenvalue of approximately 2.055555 in bv_n19 and approximately five zero eigenvalues in the random case. The two LAPACK implementations returned different valid bases, which led the greedy discrete placement search to different local layouts. Fixed placement plus orientation lowered identically; the divergence begins in placement selection.

This is not the quantum computation changing between operating systems. It is the classical quantum compiler choosing different layouts. Exact cross-platform rediscovery requires canonicalizing or removing the degenerate spectral start and adding a canonical placement tie-break, then rerunning the complete search.

Clean-room reproduction protocol

  1. Use this article and the two pinned public repositories as the implementation inputs.
  2. Implement the assigned search profile from the prose above. Do not obtain or translate author search code.
  3. Before comparing detailed results, freeze the implementation, dependency lock, platform and BLAS/LAPACK identity, generated QASM hashes, commands, source archive, output, and commit hashes.
  4. Publish exact endpoint agreements, metric-only agreements, different positive endpoints, compile failures, verification failures, and skipped checks separately.
  5. Do not count frozen placement replay as optimizer reproduction. A valid search reproduction must begin with released optimized assignment and rediscover its own endpoint.

No author implementation, generated trace, frozen placement, final orientation map, custom verifier, or saved reproduction output is published with this article. If such material is later opened for review, freeze the independent work before viewing it.

What is not claimed

  • No improvement to the mathematical quantum algorithms.
  • No Shor, non-Clifford, T-gate, or magic-state-factory result. CircLS is Clifford-only at this pin.
  • No hardware runtime, hardware area, fidelity, or logical-error-rate advantage.
  • No global optimum; only a one-flip local optimum.
  • No claim that fifteen differently selected cases estimate general performance.
  • No claim of independent reproduction yet.
  • No established novelty determination. Harvest and O3LS cover nearby congestion- and layout-aware compilation territory.
