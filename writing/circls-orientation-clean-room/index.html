Can you reproduce this CircLS compiler result?

A public specification for testing whether verifier-gated birth-orientation search finds lower occupied-spacetime circuits in the released CircLS compiler.

By Richard Williams August 31, 2026 9 minute read
15 verified effects in the original macOS-arm64 environment
14/15 effects surviving a clean Linux-arm64 optimizer replay
13/15 exact optimized replays across both environments
0 author implementation files in the clean-room archive

This is an invitation to reproduce a narrow compiler result, not an announcement that the result is established.

The experiment asks whether changing the orientation in which logical data patches are introduced can reduce the physical occupied-spacetime metric produced by CircLS. The baseline is CircLS's released full configuration—not a weakened control scheduler—and every accepted result must pass the compiler's complete public verification path.

The initial study found fifteen lower-V1 circuits with no T1 latency increase. A later clean Linux replay exposed an important limitation: fourteen effects survived a fresh run of optimized assignment, but one did not. The clean-room package reports that disagreement rather than smoothing it away.

What is being tested

CircLS compiles Clifford QASM or Pauli-product measurement programs into physical Stim circuits for a lattice-surgery model. Its released full configuration includes optimized placement, terminal-measurement re-selection, first-use allocation, last-use retirement, scheduling, parallel execution where permitted, routing, physical lowering, and verification.

The tested variable is each data patch's birth orientation: X_horizontal or X_vertical. CircLS already exposes that input. The proposed contribution is narrower: use the realized physical circuit as a counterfactual cost oracle while re-running optimized placement, and accept an orientation change only after deterministic recompilation and full verification.

The exact public sources are:

  • CircLS commit 3523afeb...f72d and its paper;
  • QASMBench commit 357b9423...ebac and its paper.

The search rule

  1. Compile the circuit with CircLS's released full configuration.
  2. Flip one data patch's birth orientation.
  3. Re-run optimized placement and complete physical compilation.
  4. Reject compile failures and candidates whose V1 is not strictly lower or whose T1 increases.
  5. Recompile each metric-eligible candidate independently. Require the circuit hash and metrics to reproduce.
  6. Require silence, determinism, forced graphlike distance, and affine logical equivalence all to run and pass with no skipped field.
  7. Accept the lowest-V1 eligible candidate, breaking ties by T1 and coordinate name.
  8. Continue until a complete one-flip neighborhood contains no acceptable move.

This is coordinate descent. Its endpoint is a verified one-flip local optimum, not a global optimum.

The cheap route proxy

In a guarded zero-rotation, equal-latency regime where liveness and batch structure do not change, the source-derived prediction at distance three is:

delta V1 = ((rounds + 1) / d) × delta route cells
         = (4 / 3) × delta route cells

The proxy is only a ranker. A candidate still has to survive complete physical compilation and the unchanged verifier. No prediction applies after rotations, latency changes, walls, batch demotion, or batch restructuring.

The result that did not survive Linux

A clean Linux-arm64 run independently rebuilt CircLS and QASMBench from the public repositories, installed the frozen Python dependencies, and reran optimized assignment.

  • Thirteen cases reproduced the original optimized baseline and final hashes exactly.
  • bv_n19 retained V1 388.667 → 378.000 at T1 104 and reproduced the exact final hash, but its released baseline physical circuit differed.
  • random_holdout_12_60_303 selected a different optimized placement. The original orientation map became V1 298.000/T1 91 rather than an improvement, so this row is excluded from any platform-independent aggregate.

The likely source is numerical platform sensitivity in CircLS's optimized assignment portfolio, which uses eigendecomposition, Hungarian assignment, and approximate QAP starts. That is a source-informed hypothesis, not yet a minimal root-cause proof.

Publication-safe summary: fifteen verified original-environment results, fourteen effects surviving a clean Linux optimizer replay, and thirteen exact optimized replays.

How to perform an independent reproduction

  1. Give the reproducer only the downloadable clean-room archive.
  2. Have them obtain the pinned CircLS and QASMBench sources from their public repositories.
  3. Have them implement the method from the prose rather than translating author code.
  4. Require them to freeze their implementation, environment, output, and hashes before seeing the full author artifact.
  5. Report exact agreements, metric-only agreements, failures, exclusions, skipped checks, and platform differences separately.

The archive exposes its components directly for inspection:

  • method specification;
  • public source pins;
  • reported results;
  • archive content manifest.

Two correctness fixes are separate

The wider review artifact also contains two CircLS corrections. They are deliberately not counted as orientation-search performance:

  • a fallback-bus persistence fix that rescues a hard compiler failure, but is not a speedup;
  • a symbolic-reporting fix that corrects a false-negative logical verdict without changing the physical circuit.

The clean-room results describe those observations, but the archive withholds the author patches.

What is not claimed

  • No hardware runtime or hardware-area advantage.
  • No non-Clifford, magic-state, or Shor improvement. CircLS is Clifford-only at this pin.
  • No global optimum.
  • No claim to broad novelty in congestion-aware compilation or layout awareness. Harvest and O3LS already cover important nearby territory.
  • No peer-reviewed novelty determination.

Report what you find

Successful reproductions, failures, partial agreements, and counterexamples are all useful. If you attempt the clean-room implementation, please preserve your source pins, dependency versions, platform, commands, output, and hashes.

Open a reproduction report on GitHub. Please do not optimize the report for agreement; platform failures and negative results are part of the evidence.
